# Persistent E2E World — Refactor Plan

## Goal

Make the `MinecraftDeviceE2EUITests` / calibration flow reuse a single `craftberry test` world across runs and scenarios, instead of creating + deleting a world for every recipe/scenario. The world is created once if absent and left in place; after each scenario the imported behavior/resource packs are deactivated for the reused world and deleted from the device so packs do not accumulate.

## Success Criteria

- First run when no `craftberry test` world exists creates it (same Creative + Cheats + seed `12345678` flow) and proceeds to pack activation + crafting verification.
- Subsequent runs / subsequent scenarios in the same suite reuse the existing world — no 45s `Create New World` + 45s `Wait for fresh world to finish loading` pair.
- After each scenario the world remains but its `world_behavior_packs.json` / `world_resource_packs.json` are reset to `[]` and every `Generated by Craftberry` pack folder is removed from `behavior_packs/` and `resource_packs/`. `craftberry test` world directory is **not** deleted.
- Pack count does not grow across consecutive `scripts/ios-device.sh minecraft-e2e redstone && scripts/ios-device.sh minecraft-e2e emerald` invocations (verified via `scripts/minecraft-cleanup.sh status`).
- Total wall time for a 2-scenario sequential run drops by ~80–90 s (one world creation skipped).
- Existing calibrated coordinates and OCR gates for non-creation steps remain unchanged; `CAPABILITIES.md` device-verified flows still pass.

## Context And Current Facts

### Current flow (`CraftberryUITests/Support/MinecraftE2EHarness.swift:17-102`, `CraftberryUITests/MinecraftDeviceE2EConfig.json:1-399`)

1. Build Craftberry fixture, export `.mcaddon`, import via share sheet, cold-launch Minecraft.
2. `configuration.steps.phased(as: .config)` is a **single flat array** that always does: `Tap Play → wait → Tap Create new world → wait → Tap Create new world from scratch → wait → Focus name field → type " craftberry test" → Toggle Creative → wait → scroll sidebar → Open Cheats → Activate Cheats → Open Advanced → type seed 12345678 → scroll back → Tap CREATE → wait achievements dialog → Confirm Create anyway → wait 45s for world load → Open pause menu → Save and quit → wait → Tap edit icon for `craftberry test` world → scroll → Open Behavior Packs → Activate imported behavior pack → accept "Update world?" → wait → verify Active → Open Resource Packs → verify auto-activated resource pack → scroll back → Tap Play → wait 45s → /tp → /setblock crafting_table → tap table → verify "Crafting"`. Then `compiler.compile(scenario.craftingPlan).phased(as: .crafting)` runs the per-scenario crafting verifications.
3. No branching on existing world; every `testCraftberry*` method (`MinecraftDeviceE2EUITests.swift:14-44`) calls `harness.run(...)` which replays the whole config sequence.
4. `scripts/minecraft-cleanup.sh` (`cmd_clean`) today is called from `scripts/ios-device.sh:262` and `scripts/minecraft-calibrate.sh:634` as `clean --delete-world --yes` — it **always** deletes both pack folders **and** the matching world directory (`afc rm -rf "$AFC_BASE/minecraftWorlds/$name"`). `find_world_dir_names` uses substring match on `levelname.txt` containing `$WORLD_NAME` (default `craftberry test`).
5. `scripts/ios-device.sh:205-274` `minecraft_e2e_on_device` runs **one** `xcodebuild -only-testing:<single selector>` per invocation, then terminates Minecraft and runs the `--delete-world` cleanup. Sequential multi-scenario runs each pay the full creation cost.
6. `CraftberryUITests/Support/MinecraftCalibrationHarness.swift:22-131` mirrors the same monolithic creation flow before starting the `NWListener` on `8765`. `scripts/minecraft-calibrate.sh:stop` also does `clean --delete-world --yes` by default.
7. `MinecraftStepExecutor.swift:47-144` already isolates per-step execution and reports `MinecraftStepResult` without `XCTFail`, so conditional execution is feasible. `MinecraftCalibrationController.swift` owns a cursor over `allSteps` and can be adapted to a split plan.
8. Pack identity is fresh per build (`--ui-testing-fresh-pack-identity` in harness `launchArguments`), so leftover packs from a prior run have distinct UUIDs and would remain active-referenced unless cleared.
9. Inventory / staging residue: after crafting the first recipe the harness returns part-used ingredient stacks to slots 2…5 (`slotAfterIngredientsReturn` in `MinecraftDeviceE2EUITests.swift:57`). No `/clear` is run today; the world is deleted so residue is irrelevant. With a reused world, leftover items, the placed crafting table, and player position persist across runs.

## Constraints And Non-goals

- **Constraints**
  - Minecraft must be fully quit before any AFC read/write of `minecraftWorlds/` or `_packs/` (`minecraft-cleanup.sh:43-50` confirmed live: AFC view is unreliable while running). This already holds for the host-side cleanup path; any per-test XCTest-internal cleanup cannot use AFC.
  - Ore UI has no accessibility elements (`docs/MINECRAFT_DEVICE_AUTOMATION.md`); world existence must be detected either by UI-visible signal (OCR/screenshot) or host-side AFC `status` before launch. AFC is authoritative; OCR is the only in-process signal.
  - `--ui-testing-fresh-pack-identity` must stay (tests need unique pack UUIDs per build); cleanup must therefore handle arbitrary UUIDs, not a fixed set.
  - Do not require new device permissions, kernel extensions, or recovery-mode changes — AFC via `afcclient --documents` is the existing transport.
  - Keep Behavio(u)r/Resource activation flow after creation identical to today so calibrated coordinates are not invalidated.

- **Non-goals**
  - Not changing the compiler, fixture generation, or `ExamplePromptLibrary`.
  - Not adding a new Bedrock profile or world template/schematic.
  - Not parallelizing scenarios on one device (still one Minecraft at a time).
  - Not moving the E2E suite to simulators or Appium.

## Key Decisions

### 1. Where to detect "world already exists"

**Recommended: two-layer check — host-side AFC `status` as fast path, XCTest OCR as fallback.**

- Host scripts (`ios-device.sh`, `minecraft-calibrate.sh`) run `minecraft-cleanup.sh status` (read-only AFC) before `xcodebuild`. If any `craftberry test` world dir exists, pass a launch-environment flag (e.g. `CRAFTBERRY_E2E_REUSE_WORLD=1`) into the XCTest process. XCTest harness reads that flag via `ProcessInfo.processInfo.environment` and skips creation steps.
- Inside XCTest, if the flag is absent or stale (AFC was wrong because Minecraft was still running), do an additional OCR check on the world-list screen: after `Tap Play` + 8s wait, OCR for `craftberry test`. If found, treat as existing; if not, run creation branch.
- **Rejected:** pure in-test OCR only — works but adds ~8s to every run even when host already knows the answer, and OCR on the world list is fragile to sort order/scrolling.
- **Rejected:** pure host-side creation (script creates world via AFC file layout) — Minecraft world format is not trivially constructible; creating via the game's own UI once is more faithful and reuses existing calibrated steps.

### 2. How to split the config plan

**Recommended: partition `MinecraftDeviceE2EConfig.json` steps into three named sections in code, not in the JSON file itself, to avoid recalibration churn.**

- `worldCreationSteps`: from "Open the world list" through "Wait for the fresh world to finish loading" + "Save and quit to the world list" / "Wait for the world list" — i.e. everything that only makes sense when the world is new (steps 1–38 up to `save-and-quit`). This block is skipped when reusing.
- `worldActivationSteps`: from "Open the craftberry test world edit screen" through "Launch the craftberry test world locally in creative mode" + 45s wait — packs activation + re-enter world. Always runs.
- `craftingStagingSteps`: `Teleports`, `/setblock crafting_table`, open table, verify "Crafting". Always runs (idempotent).
- Keep the JSON as a single array for now; introduce Swift constants with slice indices derived from step names (e.g. find index of `"Save and quit to the world list"`). Add named constants + unit test so reordering the JSON fails the test rather than silently skipping wrong steps. A future follow-up can physically split the JSON into `worldCreation` / `activation` / `staging` keys if desired.

**Alternative considered:** physically split JSON into three top-level keys now. Rejected for this increment because it requires re-calibrating tooling that reads the JSON and risks drift; slicing in Swift is lower-churn and reversible.

### 3. How to clean up after each test

**Recommended: two-tier cleanup — lightweight in-test inventory reset + authoritative host-side pack deactivation/deletion.**

- **In-test (XCTest, while Minecraft is running):**
  - Run `/clear @s` (or `/clear @s <item>`) and `/kill @e[type=item]`-style cleanup chat commands to empty inventory and dropped items, so the next scenario starts with an empty hotbar. The hotbar-slot math (`firstCraftSlot` / `slotAfterIngredientsReturn`) assumes an empty hotbar at recipe start. A `/clear` step after each scenario's crafting block restores that invariant without deleting the world.
  - Optionally break the placed crafting table (`/setblock 98 80 95 air` then re-place at next run) or leave it — re-running `/setblock 98 80 95 crafting_table` is idempotent so it can stay.
  - Do **not** attempt to deactivate packs via UI taps inside XCTest — the UI flow for deactivating is longer than activation and AFC reset is more reliable.

- **Host-side (Mac, after `xcodebuild` exits and Minecraft is terminated):**
  - Run `scripts/minecraft-cleanup.sh clean --yes` **without** `--delete-world`. This already does the desired behavior: `find_world_dir_names` locates the `craftberry test` world(s), resets their `world_behavior_packs.json` / `world_resource_packs.json` to `[]` via `afc put`, then deletes every `behavior_packs/<name>` and `resource_packs/<name>` whose `manifest.json` `header.description == "Generated by Craftberry"` (`minecraft-cleanup.sh:196-232`). The world directory is left intact.
  - Change `scripts/ios-device.sh:262` and `scripts/minecraft-calibrate.sh:634` to call `clean --yes` (not `clean --delete-world --yes`). Add a new explicit entry `clean --delete-world --yes` only for a manual `scripts/minecraft-cleanup.sh` invocation when the tester truly wants to nuke the world.

**Rejected:** deactivate packs via UI "Remove from Active" taps inside XCTest — would require calibrating 6+ new tap/OCR steps that are strictly less reliable than the existing AFC JSON reset, and AFC is already proven live.

**Rejected:** delete-and-recreate world every N runs to "defragment" — unnecessary; the seed and game rules never change and inventory is cleared. Add a `scripts/minecraft-cleanup.sh clean --delete-world --yes` escape hatch for the rare case the world gets corrupted.

### 4. Multi-scenario suite execution

**Recommended: keep `xcodebuild -only-testing:` per scenario (current `ios-device.sh` model) but add a `minecraft-e2e-all` convenience that loops scenarios with pack-only cleanup between each, preserving the world.**

- `scripts/ios-device.sh minecraft-e2e redstone` → does: AFC `status` → `xcodebuild` for redstone → terminate → `minecraft-cleanup.sh clean --yes` (world preserved).
- Immediately after, `scripts/ios-device.sh minecraft-e2e emerald` finds the existing world via AFC, reuses it, and again cleans packs only.
- Add `minecraft-e2e-all` that does `for s in redstone emerald weapon armor; do minecraft_e2e_on_device $s || break; done` with the same per-iteration cleanup. Total time ~ (1 × world creation) + N × (pack activation + crafting) instead of N × (creation + activation + crafting).
- **Rejected:** switch to a single `xcodebuild` invocation with 4 test methods in one run and do intra-process AFC cleanup — impossible because AFC cannot safely read while Minecraft is running, and the XCTest process cannot call `afcclient` on the Mac. Inter-invocation cleanup is the correct boundary.

### 5. Calibration harness parity

**Recommended: mirror the same split and cleanup in `MinecraftCalibrationHarness` and `minecraft-calibrate.sh`.**

- `minecraft-calibrate.sh start <scenario>` already does AFC `status` implicitly via session tracking; add explicit pre-check and pass `MINECRAFT_CALIBRATION_REUSE_WORLD` env. The harness's `runCalibration` should honor it.
- `minecraft-calibrate.sh stop` default should become pack-only cleanup (`clean --yes`), with `stop --delete-world` for the old behavior. Keep `--keep-state` as "do nothing".

## Recommended Approach

### Overview

```
Host (Mac)                              Device (Minecraft)
---------                               ------
ios-device.sh minecraft-e2e redstone
  ├─ AFC status: does "craftberry test" exist?
  │   yes → set CRAFTBERRY_E2E_REUSE_WORLD=1
  │   no  → set 0
  ├─ xcodebuild -only-testing:Redstone
  │     └─ MinecraftE2EHarness.run(...)
  │           ├─ Craftberry generate/build/export/import (always)
  │           ├─ Cold launch Minecraft
  │           ├─ If reuse==1 or OCR finds world → skip creationSteps
  │           │  else run creationSteps (once)
  │           ├─ run activationSteps (edit world → activate packs → Play)
  │           ├─ run stagingSteps (/tp + /setblock + open table)
  │           ├─ run craftingSteps (per-scenario compiler output)
  │           └─ run cleanupStagingSteps (/clear @s, optional /setblock air)
  ├─ terminate Minecraft (devicectl)
  └─ AFC: reset world_*.json to [], rm Generated-by-Craftberry packs
        (world directory left intact)

Next scenario repeats — world now exists so creation is skipped.
```

### What changes where

1. **`MinecraftDeviceE2EConfig.json` + harness slicing**
   - Do not change JSON shape in this increment (avoid recalibration). Add Swift `MinecraftE2EStepSlices` that partitions `configuration.steps` by sentinel step names.

2. **`MinecraftE2EHarness.swift`**
   - Inject `worldExists: Bool` derived from `ProcessInfo.processInfo.environment["CRAFTBERRY_E2E_REUSE_WORLD"]` plus fallback OCR check on the world list after the initial `Tap Play`.
   - Change `run(_:)` to execute phases conditionally: `if !worldExists { run(worldCreationSteps) }`, then always `run(activationSteps)`, `run(stagingSteps)`, `run(craftingSteps)`, then run a small `postScenarioCleanupSteps` (`/clear @s`, `/kill @e[type=item]` if reliable, or just `/clear`).
   - Keep `MinecraftStepExecutor` unchanged; only the harness's orchestration changes.

3. **`MinecraftCalibrationHarness.swift` + `MinecraftCalibrationController.swift`**
   - Same conditional creation logic for calibration server startup. The controller's `allSteps` becomes `creationSteps + activationSteps + stagingSteps + craftingSteps` when `worldExists==false`, otherwise `activationSteps + stagingSteps + craftingSteps`.

4. **`scripts/minecraft-cleanup.sh`**
   - No logic change needed for the new default — `clean --yes` already is "delete packs only, reset world packs to []". Clarify `usage()` text to emphasize that `clean --yes` preserves the world and `clean --delete-world --yes` is now the exceptional nuke path. Optionally add alias `clean --keep-world` for clarity (maps to same as no flag).

5. **`scripts/ios-device.sh`**
   - Add `afc_world_exists()` helper (calls `minecraft-cleanup.sh status` or directly `afcclient ls` + `levelname.txt` check, reusing `find_world_dir_names` logic).
   - In `minecraft_e2e_on_device`, before `xcodebuild`, probe and export env: `CRAFTBERRY_E2E_REUSE_WORLD=1/0` into the `xcodebuild test` invocation (`env CRAFTBERRY_E2E_REUSE_WORLD=... xcodebuild ...` or `CRAFTBERRY_E2E_REUSE_WORLD=... xcodebuild ...`).
   - Change cleanup call from `"$CLEANUP_SCRIPT" clean --delete-world --yes` to `"$CLEANUP_SCRIPT" clean --yes`.
   - Add `minecraft-e2e-all` subcommand looping `redstone emerald weapon armor` with per-iteration cleanup. Add `minecraft-e2e-nuke` (or `minecraft-e2e --fresh-world`) that does `clean --delete-world --yes` before the run for when a truly fresh world is needed.

6. **`scripts/minecraft-calibrate.sh`**
   - Same env plumbing (`MINECRAFT_CALIBRATION_REUSE_WORLD`) and change `cmd_stop` default cleanup to `clean --yes`. Add `stop --delete-world` to opt into world deletion.

7. **`docs/MINECRAFT_DEVICE_AUTOMATION.md` + `README.md`**
   - Update "Deleting test worlds and installed packs after a test (cleanup)" section to document the new default (packs only) and the explicit `--delete-world` escape hatch, and the `minecraft-e2e-all` flow.

### Residual state that must be handled without deleting the world

| Residue | Why it matters | Mitigation |
|---|---|---|
| Previous packs still in `*_packs/` and still referenced by world | Activating a new pack while old pack is Active can cause duplicate-item warnings or hit the pack limit | Host AFC reset: `world_*_packs.json → []` + `rm -rf *_packs/<craftberry>` — authoritative |
| Items in player inventory / hotbar | `firstCraftSlot`/`slotAfterIngredientsReturn` math assumes empty hotbar | In-test `/clear @s` chat command after crafting block; verify with OCR that hotbar is empty before next scenario |
| Dropped item entities on ground | Visual clutter, could be picked up | `/kill @e[type=item]` or `/clear` already covers; re-tp to staging position |
| Placed crafting table at `98 80 95` | Next run's `/setblock` would overwrite anyway | Leave in place; `/setblock crafting_table` is idempotent; optionally `/setblock air` in cleanup |
| Player position / health / effects | Next run re-teleports to `100 80 95 90 45` | Always re-run teleport staging step |
| Seed / game rules / cheats | Must remain Creative + Cheats enabled, seed 12345678 | Created once; reuse preserves them. If world is reused but seed mismatched, the seed field is not re-entered — document that `nuke` is required if seed changes |

Highest-risk validation: the OCR world-existence fallback inside XCTest. ## Risks / Rollback

- **World corruption / seed drift:** Reusing the world means a corrupted world or a seed change (e.g. if `12345678` is later changed in config) persists. Mitigation: `scripts/minecraft-cleanup.sh clean --delete-world --yes` / `ios-device.sh minecraft-e2e --fresh-world` nukes it; document when to use it (seed change, checklist when E2E flakes).
- **Inventory residue causing crafting-slot math to break:** `/clear @s` must reliably empty the hotbar; if it fails (chat command mistyped or UI not ready), the next recipe's `firstCraftSlot` assumption breaks and the wrong slot is tapped. Mitigation: add OCR or wait after `/clear`; on failure retain a fallback of deleting the world as last resort and re-creating.
- **Pack limit / dangling ACTIVE references:** If host cleanup fails (AFC unreachable, Minecraft not fully terminated), old packs remain ACTIVE and the world edit screen may show multiple packs. Mitigation: the 45s-activation OCR will still look for `$EXPECTED_BEHAVIOR_PACK` (the new pack's name), but `ACTIVE in craftberry test` counts in `status` will surface accumulation; `ios-device.sh` should log `status` before and after cleanup.
- **Step-slice fragility:** Sentinel names in JSON changing breaks slicing. Mitigation: unit test pins sentinels; failure is loud.
- **Rollback:** Every change is reversible by restoring the single-flag behavior: change `ios-device.sh`/`minecraft-calibrate.sh` back to `clean --delete-world --yes` and unset `CRAFTBERRY_E2E_REUSE_WORLD`, which restores the current always-create flow. No data migration is needed.

## Open Questions

- Should `/clear @s` be a single chat command step or two (`/clear` then `/kill @e[type=item]`) to purge dropped items? Decision: start with `/clear @s` only (simpler, one chat round-trip); add `/kill` if device testing shows ground items interfere. Confirmation needs one device run.
- Should the in-test cleanup also `/setblock 98 80 95 air` or leave the crafting table standing? Leaving it is idempotent via next run's `/setblock crafting_table`; clearing is cleaner for debugging. Decision: leave by default, add air-clear only if table duplication bugs appear.
- Does `CRAFTBERRY_E2E_REUSE_WORLD` need a distinct value per scenario to force recreation for the first scenario of `minecraft-e2e-all` only? No — the first invocation in `minecraft-e2e-all` will see no world and create; subsequent loop iterations will see it and reuse. A single boolean per-invocation suffices.
- Should `MinecraftDeviceE2EConfig.json` be split into `worldCreation` / `activation` / `staging` keys in this increment? Deferred to a follow-up to keep recalibration risk low; revisit if sentinel-based slicing proves brittle over two device cycles.
